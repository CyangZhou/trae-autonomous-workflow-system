## 🧠 费曼学习法引擎

### 核心原则

> "如果你不能简单地解释它，你就没有真正理解它。" —— 理查德·费曼

**三大铁律**：

| 铁律 | 执行标准 | 检查点 |
|:---:|:---------|:-------|
| **1. 降维打击** | 每个概念必须能用"给12岁孩子解释"的方式重述 | □ 有通俗类比？ |
| **2. 难易一致** | 全篇阅读难度波动不超过 15% | □ 无突兀专业术语？ |
| **3. 闭环验证** | 每个章节必须包含"一句话总结" | □ 有核心要点？ |

### 费曼四步法（强制执行）

```
┌─────────────────────────────────────────────────────────────┐
│                    费曼四步法执行流程                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【第一步：选择概念】                                         │
│  ├─ 识别文档中的核心概念（≥3个）                              │
│  ├─ 标记专业术语（用 📌 符号）                                │
│  └─ 输出：概念清单 + 术语表                                   │
│                                                             │
│  【第二步：教给孩子】                                         │
│  ├─ 为每个概念创建"通俗版解释"                                │
│  ├─ 使用类比：生活场景 > 抽象比喻                             │
│  └─ 输出：每个概念的"一句话说人话"版本                        │
│                                                             │
│  【第三步：识别漏洞】                                         │
│  ├─ 检查解释中的"卡顿点"                                     │
│  ├─ 标记需要补充背景知识的部分                                │
│  └─ 输出：漏洞清单 + 补充材料                                 │
│                                                             │
│  【第四步：简化重组】                                         │
│  ├─ 用更简单的语言重写                                       │
│  ├─ 确保全篇难易度一致                                       │
│  └─ 输出：最终优化版文档                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 难易度一致性校准器

**校准公式**：
```
难度分数 = (专业术语密度 × 0.4) + (句子平均长度 × 0.3) + (抽象概念占比 × 0.3)

目标：全篇难度分数波动 < 15%
```

**执行标准**：

| 段落类型 | 难度分数 | 处理方式 |
|:---------|:---------|:---------|
| 过于简单 | < 0.3 | 适当增加深度，补充背景 |
| 适中 | 0.3 - 0.6 | 保持现状 |
| 过于复杂 | > 0.6 | 必须降维，添加类比 |

### 飞书原生组件使用指南

#### 1. 标题层级规范

| 层级 | 用途 | 格式示例 |
|:---:|:-----|:---------|
| H1 | 文档主标题（仅1个） | `# 文档标题` |
| H2 | 章节标题（3-7个） | `## 第一章` |
| H3 | 小节标题 | `### 1.1 背景` |
| H4 | 细分标题（慎用） | `#### 详细说明` |

**⚠️ 禁止**：
- 跳级使用（H1 → H3）
- 同级标题过多（> 10个）
- 标题过长（> 20字）

#### 2. 高亮块系统

```
💡 提示块 - 友好提醒
📌 重点块 - 核心概念
⚠️ 警告块 - 注意事项
✅ 成功块 - 完成状态
❌ 错误块 - 常见问题
📝 笔记块 - 补充说明
```

**使用规则**：
- 每个高亮块必须有明确的图标
- 内容不超过 3 行
- 全篇高亮块数量 ≤ 章节数 × 2

#### 3. 表格设计规范

**✅ 正确示例**：

| 功能模块 | 核心价值 | 实现难度 |
|:---------|:---------|:--------:|
| 用户认证 | 安全保障 | ⭐⭐ |
| 数据分析 | 决策支持 | ⭐⭐⭐ |
| 支付系统 | 商业变现 | ⭐⭐⭐⭐ |

**❌ 错误示例**：

| 功能 | 说明 |
|---|---|
| 认证 | 用户登录功能，支持多种登录方式，包括手机号、邮箱、第三方登录等 |
| 分析 | 数据分析模块，提供实时数据看板，支持自定义报表导出 |

**表格设计原则**：
- 列数控制在 3-5 列
- 单元格内容不超过 2 行
- 使用对齐符号 `:---` `:---:` `---:` 控制对齐
- 表头必须加粗或使用醒目样式

#### 4. 列表系统

**无序列表**（用于并列关系）：
- 要点一
- 要点二
- 要点三

**有序列表**（用于步骤/流程）：
1. 第一步：准备阶段
2. 第二步：执行阶段
3. 第三步：验收阶段

**嵌套列表**（层级不超过3层）：
- 一级要点
  - 二级要点
    - 三级要点

#### 5. 代码块规范

**行内代码**：使用反引号包裹，如 `function_name()`

**代码块**：使用三反引号 + 语言标识

```python
def hello_world():
    print("Hello, Feishu!")
```

**代码块规则**：
- 必须标注语言类型
- 代码不超过 20 行
- 关键行添加注释

## 📱 移动端适配规范

### 阅读体验优化

| 问题 | 解决方案 |
|:-----|:---------|
| 表格过宽 | 拆分为多个小表格或转为列表 |
| 代码块过长 | 截断关键部分，添加折叠提示 |
| 图片过大 | 限制宽度为 100%，居中显示 |
| 段落过长 | 每段不超过 4 行，增加空行 |

### 移动端友好检查清单

- [ ] 表格列数 ≤ 4
- [ ] 代码块行数 ≤ 15
- [ ] 图片有替代文本
- [ ] 关键信息在前 3 行可见

## 🎨 示例：优化前后对比

### ❌ 优化前

```
微服务架构是一种将单一应用程序开发为一组小型服务的方法，每个服务运行在自己的进程中，并使用轻量级机制（通常是HTTP资源API）进行通信。这些服务围绕业务能力构建，并可通过全自动部署机制独立部署。这些服务可以用不同的编程语言编写，使用不同的数据存储技术。
```

### ✅ 优化后

```
📌 什么是微服务？

想象一家餐厅：
- 传统架构 = 一个大厨做所有菜（前菜、主菜、甜点）
- 微服务架构 = 三个厨师各司其职（前菜师、主菜师、甜点师）

微服务就是把一个大系统拆成多个小服务，每个服务只做一件事，互不干扰。

💡 核心价值：改一个功能，不影响其他功能
```
